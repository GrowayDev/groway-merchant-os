    46→## 4. Architecture
    47→
    48→### 4.1 Decision: a modular monolith inside the Groway repository
    49→
    50→Tshepo is TypeScript modules under `src/lib/tshepo` with route handlers under `src/app/api/tshepo`. Every external dependency (database, payment provider, feature data, messaging) sits behind a port, so a module can be extracted into a service later if a measured need appears. Kubernetes, a separate feature store and a message broker are not needed in the early waves.
    51→
    52→### 4.2 Modules
    53→
    54→| Module | Responsibility | Status |
    55→| --- | --- | --- |
    56→| ledger | Double-entry posting, idempotency, outbox port, trial balance | Built and tested |
    57→| consent | Purpose-bound, revocable, expiring consent log | Built and tested |
    58→| repayment | Waterfall allocation and the settlement split rule | Built and tested |
    59→| gopay | Capture, fee, settlement, split, payout, debit-order route, refusal while GoPay is not live | Built and tested |
    60→| decisioning | Consent first, features, hard stops, affordability, reason codes, trace | Built and tested |
    61→| edge | Signed offline decision envelopes and spend caps | Built and tested |
    62→| Prisma ledger adapter | Writes entry, lines and outbox in one transaction | Built; tested against a fake client only |
    63→| mobile money rail | Provider-neutral collections and payouts for Malawi | Specified in section 13; not built |
    64→| consumer wallet | Wallet accounts, limits, payments, repayments | Specified in section 6.6; not built |
    65→| routes and screens | API handlers and admin screens | Not built |
    66→
    67→The bundle holds 24 passing tests and a schema that passes the Prisma 6 validator when merged with Groway's models. The SQL guards that enforce balanced entries and append-only tables have not yet run on a database.
    68→
    69→### 4.3 Data and money rules
    70→
    71→- All money in new code is integer minor units (cents, tambala) held as BigInt, with an ISO currency code. Never floating point.
    72→- Each currency has its own ledger accounts. Rand and Malawi kwacha are never netted; conversion is an explicit entry with a recorded rate and source.
    73→- The existing accounting journal stays for accounting. Tshepo has its own ledger tables linked by source type and source ID, and posts summary entries to accounting.
    74→- Float columns in older tables become read-only mirrors. New money movements go to the ledger first.
    75→- Every tenant-scoped table carries a tenant key. Every Tshepo route applies a tenant guard before reading or writing.
    76→- Events are written to a Postgres outbox in the same transaction as the ledger entry, and a worker publishes them. A message broker is added only when a measured threshold is crossed.
    77→
    78→### 4.4 Security baseline
    79→
    80→- NextAuth and JWT stay. Staff and agent accounts use multi-factor sign-in.
    81→- Personal data is tokenised on ingestion; raw identifiers live only in the identity and KYC code paths.
    82→- Secrets come from the environment or a secret manager, never from the repository. The `.env` file is never committed.
    83→- TLS everywhere; the Mac server is reached only through a Cloudflare tunnel; no router ports are opened.
    84→- Provider callbacks are verified, replay-protected and idempotent (section 13.5).
    85→- Append-only enforcement on ledger and consent tables is done in the database, not only in code.

   100→
   101→Cloudflare provides the domain, protection and the tunnel to the Mac. Staging uses its own sub-address, locked to your email through Cloudflare Access. The current live site is left alone until staging has run cleanly.
   102→
   103→### 5.3 Criteria for moving to hosted production
   104→
   105→Hosted Postgres in a South African region with automated backups and point-in-time recovery; an uptime target and an on-call owner; backup restores tested; secrets in a manager; staging and production separated; penetration test closed; licences and agreements for the first product in place. The Mac server never carries live credit or payments.
   106→
   107→### 5.4 Operations
   108→
   109→One database client per process with query logging off by default; Sentry for errors; structured logs with a correlation ID on every request; daily encrypted backups copied off the machine with a monthly restore test; runbooks for ledger imbalance, provider outage, decision latency, consent backlog, data breach, key compromise and data requests.

   111→## 6. Product build specifications
   112→
   113→### 6.1 Ledger
   114→
   115→Accounts, journal entries and lines, with signed amounts (debit positive, credit negative). Rules: every entry nets to zero; no zero lines; idempotency key unique per tenant; reversals are new entries; balances come from lines. The Prisma adapter commits entry, lines and outbox row in one transaction. Database triggers reject unbalanced entries at commit and block update and delete on ledger and consent tables.
   116→
   117→### 6.2 GoPay end to end (disabled until licensed)
   118→
   119→Customer pays at the till on a supported rail (QR or PayShap, instant EFT, debit card, credit card). A licensed partner authorises the payment. GoPay deducts the merchant fee, settles into the trust account, applies any repayment share, and pays out the remainder. Each stage is a ledger entry with its own idempotency key, so a replay changes nothing. In the debit-order route the partner collects repayments on a schedule and failures raise arrears. The split route refuses to run while the live flag is off.
   120→
   121→### 6.3 Decisioning and GroCredit
   122→
   123→GroCredit tiers and the NCA flags become the policy input. The orchestrator checks consent first, reads features, applies hard stops (identity check, arrears, tenure), runs affordability, then returns an outcome, a limit, reason codes, a counterfactual and a trace carrying policy and model versions. Missing critical data means refer to a human, never a guess. The decision step is where the first scorecard is plugged in.
   124→
   125→### 6.4 Repayment and collections
   126→
   127→Waterfall order is product configuration approved by compliance. Collections handles arrears buckets, customer messaging, promise-to-pay, hardship and restructuring before any escalation. Grant-linked products enforce a minimum retained amount and a cap on total deductions. Every adverse outcome has a human review path.
   128→
   129→### 6.5 Edge and SmartPole
   130→
   131→A small Node agent on the hub appliance holds signed eligibility envelopes (Ed25519), verifies signature, tenant, key ID and expiry offline, tracks spend against the cap, and syncs over WiFi, LTE or satellite. Offline limits stay small until early hubs show clean reconciliation.
   132→
   133→### 6.6 Consumer wallet (restored from the older build file)
   134→
   135→| Area | Specification |
   136→| --- | --- |
   137→| Wallet core | Ledger account kind `consumer_wallet`; limits and KYC levels 0 to 4 as policy; savings pockets; history and export; disputes |
   138→| Payments | QR, peer-to-peer, PayShap, request and split, scheduled payments, beneficiaries; offline tokens reuse the signed-envelope design |
   139→| Services | Bills, airtime, remittance, vouchers, ticketing, prepaid electricity through licensed partners |
   140→| Credit | BNPL, earned wage access and layby shells on the Tshepo decision engine; repayment may come from the wallet |
   141→| Performance fixes | Split the 556 KB page into five tabs loaded on demand, paginate lists, remove backup copies from the app folder, query logging off, a bundle size limit in CI |
   142→| Gate | Holding customer funds is regulated: settle the licence route or a licensed partner first |

   216→### 13.1 The three names and what they mean in Malawi
   217→
   218→| Name | What it is | How Groway reaches it |
   219→| --- | --- | --- |
   220→| Airtel Money | Airtel Malawi's wallet; one of the two main mobile money operators | Through a licensed aggregator first; direct operator integration later for cost |

   226→### 13.2 Approach: start with a licensed partner
   227→
   228→Groway does not issue e-money or run a payment system in Malawi in the first phases. It integrates through payment service providers that the Reserve Bank of Malawi (RBM) has licensed, behind a provider-neutral interface so providers can be swapped or combined.
   229→
   230→| Criterion | pawaPay | PayChangu | Direct operator integration |
   231→| --- | --- | --- | --- |
   232→| Malawi operators | Airtel and TNM, in kwacha | Airtel Money and Mpamba | One integration per operator |
   233→| Services | Collections and payouts through one asynchronous API, with callbacks | Collections (hosted checkout and direct charge), payouts to wallets and banks, bill payments (for example water and electricity), airtime, cards, USD virtual accounts | Depends on the operator |
   234→| Licence | Reported to hold an RBM payment service provider licence | Reported to hold an RBM licence effective 30 September 2026 | Operator-licensed |
   235→| Other countries | About 23 countries, useful for later expansion | Malawi focus | None |
   236→| Fees, limits, settlement terms | To obtain | To obtain | To negotiate |

   252→### 13.4 Rail design
   253→
   254→The Tshepo mobile money rail is a provider-neutral interface, in the same ports-and-adapters style as the ledger:
   255→
   256→```ts
   257→interface MobileMoneyRail {
   258→  provider: 'pawapay' | 'paychangu';
   259→  collect(req: CollectRequest): Promise<RailAccepted>;   // customer approves on handset
   260→  payout(req: PayoutRequest): Promise<RailAccepted>;
   261→  status(reference: string): Promise<RailStatus>;
   262→  parseCallback(headers: Headers, body: string): VerifiedEvent; // throws if invalid
   263→  operators(): Promise<Operator[]>;                      // AIRTEL_MWI, TNM_MWI
   264→}
   265→
   266→type CollectRequest = {
   267→  reference: string;        // equals the ledger idempotency key
   268→  amountMinor: bigint;      // kwacha in tambala
   269→  currency: 'MWK';
   270→  msisdn: string;           // +265...
   271→  operator: 'AIRTEL_MWI' | 'TNM_MWI';
   272→  purpose: string;
   273→};
   274→```
   275→
   276→**Transaction states:** created, accepted by provider, waiting for the customer, then completed, failed, timed out, or unknown. Unknown is never treated as success: it is polled until final and reconciled.
   277→
   278→**Ledger postings (kwacha accounts kept separate from rand):**
   279→
   280→| Event | Entry |
   281→| --- | --- |
   282→| Collection completed | Debit mobile money clearing (per provider), credit merchant wallet or sales account |
   283→| Fee charged | Debit merchant wallet, credit fee income; provider cost to a cost account |
   284→| Provider settles to the kwacha bank account | Debit trust bank (kwacha), credit mobile money clearing |
   285→| Payout accepted | Debit wallet, credit payout pending (a reserve) |
   286→| Payout completed | Debit payout pending, credit mobile money clearing |
   287→| Payout failed | Reverse the reserve |
   288→
   289→Amount precision differs by provider and operator, so each provider adapter converts between tambala and the provider's decimal rules, with tests for rounding.
   290→
   291→**Reconciliation:** a daily job compares provider reports and callbacks with the ledger and sends differences to an exceptions queue. No manual edits to ledger entries; corrections are new entries.
   292→
   293→### 13.5 Callback security and failure handling
   294→
   295→- Verify every callback signature as the provider specifies, reject stale timestamps, and store the raw payload append-only.
   296→- Answer quickly with a success code and process the event asynchronously. Process each provider reference at most once.
   297→- Always have a status poll as a fallback with backoff.
   298→
   299→| Situation | Handling |
   300→| --- | --- |
   301→| Customer ignores the prompt, enters a wrong PIN or has too little money | Mark failed, show a clear message, post nothing |
   302→| No answer before the timeout | Mark unknown, poll, reconcile; never assume success |
   303→| Duplicate callback | No effect, because of the idempotency key |
   304→| Provider outage | Circuit breaker; use the second provider for the same operator; queue payouts |
   305→| Callback for an unknown reference | Quarantine and alert |
   306→| Amount differs from the request | Hold and investigate |
   307→| Wallet limit exceeded | Show the limit message; do not retry |
   308→
   309→### 13.6 Identity, limits and fraud
   310→
   311→- Validate phone numbers (+265 and operator prefixes); use account-name checks if the provider offers them.
   312→- Keep product limits inside the operator wallet limits. RBM sets transaction and balance limits for e-money accounts under the Payment Systems (E-Money) Regulations 2019.
   313→- Map KYC levels to the national ID route *VERIFY*; reuse sanctions and politically exposed person screening.
   314→- Add velocity rules, SIM-swap signals where operators share them, a cooling-off period when a payout destination changes, and dual approval for large payouts.

   421→## 16. Top-up credit: airtime, data and electricity advances (South Africa and Malawi)
   422→
   423→This section covers the product where a customer who is short of money gets airtime, data or an electricity token now, and the advance plus a fee is taken back automatically the next time they top up or buy. Public facts below were reviewed on 11 November 2026 and are listed in 16.14. Fees and menus change, so every figure here is illustrative until confirmed with the operator or vendor. *VERIFY* marks items for counsel or a partner.
   424→
   425→### 16.1 How it works in the market today
   426→
   427→**Mechanism.** The customer asks (USSD menu, SMS, app or WhatsApp). A decision engine checks recharge or purchase history and returns the amounts they qualify for. The customer sees the fee and accepts. The airtime or token is delivered immediately. The next time they recharge or buy, the platform takes the advance and fee first and lets the rest through. That automatic claw-back is the whole model, and it only works where the platform can see and intercept the top-up.
   428→
   429→**South Africa**
   430→
   431→- **Vodacom Airtime Advance** (dial *135*082#): advances of up to R20 depending on what the customer qualifies for, with an access fee of R1.10 including VAT on one Vodacom page and R1.20 per R10 or part thereof on another. Repaid from the next recharge. Top-up and uChoose customers who do not recharge are billed (the amount is added to the bill by the end of the month; another page says after 30 days). Eligibility includes recharging at least R29 a month over three months; postpaid customers do not qualify. Vodacom says more than 10 million South Africans use it.
   432→- **MTN XtraTime** launched in 2016 as a USSD service charging a small fee instead of interest. In August 2026 MTN was reported to be cutting back airtime advances while Vodacom and Telkom lean on them.
   433→- **Cell C** offers an advance for a fixed fee per transaction with no interest.
   434→- **Optasia** is reported as the company behind the airtime lending of Vodacom and MTN, and in September 2026 was reported to be acquiring Finergi, whose technology lets prepaid electricity meters work as digital wallets with repayment at the next purchase.
   435→- **Electricity:** Blu Label offers BlueAdvance for airtime and electricity; Citiq launched an in-app electricity advance in November 2025 that takes 50% of each later purchase; WattWallet is a pay-at-month-end pilot.
   436→
   437→**Malawi**
   438→
   439→- **TNM Pasavute:** airtime credit via \*600# or an SMS, with a 10% service fee repaid on the next recharge, built with South Africa's Net1 and Supa Pesa; reported at more than 20 million requests.
   440→- **Airtel Kutapa:** borrow K50 to K2,000 with codes such as *533*50#; borrowing K50 means paying back K5 extra; needs 90 days on the network, prepaid only, and no outstanding balance.
   441→- **Airtel Kutchova:** a digital loan issued by a bank and transacted on Airtel Money; borrowers use it for airtime, food and electricity.
   442→- **TNM Mpamba Ndikankhe:** an overdraft on the Mpamba wallet after 90 days of use; agents can sell ESCOM tokens and airtime.
   443→
   444→**What this means.** Both countries already have incumbents inside the operators' own recharge systems. Groway cannot simply add a menu item to an operator's USSD flow without an operator agreement. The design below therefore starts where Groway controls the top-up.

   466→### 16.3 Three ways Groway can offer it
   467→
   468→| Model | How it works | Needs | Verdict |
   469→| --- | --- | --- | --- |
   470→| **C: Merchant float advance** | Spaza merchants who sell airtime and electricity get float on credit, repaid from their sales and vending commissions | Merchant OS data, GroCredit, the ledger | Start here: you see every sale |
   471→| **B: Channel-embedded advance** | Customers buying airtime, data or electricity through Groway's own channels (Merchant OS tills, WhatsApp, SmartPole portal, wallet, Malawi mobile money) get an advance repaid on their next purchase through those channels | A vending or aggregator agreement; consent; licensing route | Second: feasible without an operator deal, but recovery only happens where Groway sees the purchase |
   472→| **A: Operator-embedded (Optasia model)** | Groway's engine sits inside an operator's recharge flow and the operator deducts at recharge | An operator commercial and technical agreement | Later: strongest recovery, hardest to win because incumbents exist |
   473→
   474→Recovery rate is the number that decides profitability. Model C and B recover only on purchases Groway can see, so advances are sized to that reach, and recovery falls back to approved wallet or mobile money prompts.
   475→
   476→### 16.4 End-to-end flows
   477→
   478→**Airtime or data advance (South Africa and Malawi)**
   479→
   480→1. The customer asks through WhatsApp, the till, the portal or USSD (Malawi).
   481→2. Identify the subject (phone number) and check consent for credit use.
   482→3. Check eligibility and the limit; show the menu of amounts the customer qualifies for.
   483→4. Show the quote: amount, fee and total to repay. The customer accepts.
   484→5. Post the issue entry and call the vending adapter to deliver the airtime.
   485→6. On the next top-up through a Groway channel, the top-up event calls recovery. The platform takes the allowed amount, tells the vending adapter how much to pass through, posts the entry and sends a message.
   486→7. If not recovered by the due date: add to bill where an operator bill exists (South Africa top-up customers), otherwise write off after reminders and offers.
   487→
   488→**Electricity advance (meter-anchored)**
   489→
   490→1. The customer gives the meter number. The vending provider validates the meter and supply details.
   491→2. Eligibility uses purchase history for that meter and the customer's identity, so a meter changing hands does not inherit credit.
   492→3. Quote and accept. The vendor issues a single-use token on credit and it is sent by message.
   493→4. The advance is anchored to the meter number and the customer. On each later purchase through Groway's vending path, a capped share (for example 50%) goes to the advance until repaid.
   494→5. Where a municipality allocates part of a purchase to arrears, Groway's share is taken after those deductions. *VERIFY* the allocation order with the vending provider.
   495→
   496→**Electricity recovery across channels.** A customer can buy tokens at banks, retailers and apps. The debt follows the meter only if every vending channel calls Groway's recovery hook. Options, in order: become a vendor so purchases flow through Groway; agree a deduction hook with a large vending network (one report says Blu Label's platform handles over 60% of top-ups); offer a customer-approved wallet or mobile money repayment; and size advances to what Groway can recover through its own channels. Do not promise customers that repayment is automatic everywhere.
   497→
   498→**Merchant float advance**
   499→
   500→1. A merchant buying airtime or electricity stock requests float in Merchant OS.
   501→2. GroCredit tier and sales history set the limit.
   502→3. The float is delivered; repayment is taken as a share of the merchant's later vending sales or settlements.
   503→
   504→**Malawi variants**
   505→
   506→- Airtime and ESCOM tokens are bought through a licensed provider's bill and airtime interfaces (for example PayChangu's bills and airtime endpoints).
   507→- Recovery uses the mobile money payment prompt flow from section 13: when the customer next pays through Groway, the platform deducts the advance first.
   508→- Menus are in kwacha with tambala precision. Messages are in English and Chichewa.

   521→### 16.6 Technical design
   522→
   523→**Built (in `src/lib/tshepo/topup`):** product definitions and fee quotes, eligibility and limit ladder, the advance service (issue, recover, overdue), in-memory repository, and presets for the four products above.
   524→
   525→**Ledger postings (customer subject is the phone number or meter):**
   526→
   527→| Event | Entry |
   528→| --- | --- |
   529→| Advance issued | Debit advance receivable (principal plus fee); credit supplier payable (principal); credit fee income (fee) |
   530→| Recovered at a top-up | Debit collections clearing; credit advance receivable |
   531→| Written off | Debit bad debt expense; credit advance receivable |
   532→| Added to the operator bill | Receivable closed against a billed-amount account when the operator confirms; no cash is taken by Groway |
   533→
   534→**Ports still to build:**
   535→
   536→- **Vending adapter:** deliver airtime, data or an electricity token, return a reference, and confirm. One adapter per supplier or aggregator, per country.
   537→- **Top-up event source:** a webhook or stream that reports each recharge or purchase by the subject, with an idempotent reference.
   538→- **Operator or vendor settlement:** daily statements matched to the ledger, with a payable to the supplier for advanced value.
   539→- **Notifier:** WhatsApp, SMS and USSD messages for offers, confirmations and reminders.
   540→- **Data model:** add an advance record table and a consent purpose for top-up credit to the Prisma schema.
   541→- **Routes:** quote, issue, recovery (called by the vending path), status, and an overdue job, all behind the tenant guard.
   542→
   543→**Reconciliation:** daily match of supplier statements to issue and recovery entries; unknown vendor outcomes are polled and never assumed to succeed.
   544→
   545→### 16.7 Funding and economics
   546→
   547→- **Float funding:** someone pays the supplier for the airtime or electricity delivered before the customer repays. Options: lender-funded, Groway-funded, or a supplier credit line. This is a Wave 0 decision.
   548→- **Fee as a rate:** a fee of R2.40 on a R20 advance repaid in 7 days is 12% for the week. Short terms make fees look small and annual rates very high. Report both to the credit committee and regulators.
   549→- **Loss drivers:** customers who stop using the number or meter, switch SIMs, or buy through channels Groway does not see. Track recovery rate, days to recover, and net loss by cohort and channel.
   550→- **Unit economics model:** advance volume, take-up, fee, recovery rate, funding cost, supplier margin, messaging and vending costs, fraud losses. Build it before launch and keep it updated with pilot data.

   552→### 16.8 Regulation, consumer protection and responsible lending
   553→
   554→| Area | South Africa | Malawi |
   555→| --- | --- | --- |
   556→| Credit | The National Credit Act sets fee and interest ceilings, and since 2016 the registration threshold for credit providers is nil. Whether an advance with an access fee counts as a credit agreement is a legal question that operators have answered by marketing a fee, not interest. Fees charged by a separate service provider can count towards the ceiling. Get a written legal opinion before launch | Lending needs registration under the Financial Services Act regime, and incumbents issue some products through banks. *VERIFY* for any advance sold through Groway's own channel |
   557→| Electricity | Tokens are issued through vending agreements with Eskom or the municipality; municipalities may allocate part of a purchase to arrears. Reselling electricity needs a vendor agreement. *VERIFY* | ESCOM tokens are sold through licensed channels such as bank and mobile money bill payment; a vendor or provider agreement is needed. *VERIFY* |
   558→| Data | POPIA: consent for credit use, purpose limits, limits on solely automated decisions *VERIFY* | Data Protection Act 2024: lawful basis, officer, impact assessment, cross-border conditions |
   559→| Payments | Licensed partner for moving money | Licensed provider only (section 13.7) |
   560→
   561→**Responsible-lending guardrails (both countries):**
   562→
   563→- Small starter limits that rise only with repayment.
   564→- One open advance per customer; no rollover or refinancing of an unpaid advance with a new one.
   565→- A clear quote with the total to repay before acceptance, in the customer's language.
   566→- Explicit opt-in, an easy opt-out and a cap on advances per month.
   567→- A hardship route and a human review of complaints.
   568→- Press criticism of electricity advances in South Africa makes transparent pricing and fair treatment a business requirement, not just a legal one.

   570→### 16.9 Fraud and abuse controls
   571→
   572→- Phone number recycling and SIM swap: require tenure on the current SIM where the operator shares it; pause advances after a swap.
   573→- Advance farming: link accounts by device, identity and payment instrument; block repeat patterns.
   574→- Meter sharing and meter changes: bind eligibility to the meter and the verified customer.
   575→- Agent and merchant collusion: velocity rules and dual approval for large float.
   576→- Negative list: blocked identities and numbers shared across Groway products.

   674→### 17.2 The interface
   675→
   676→All suppliers sit behind one provider-neutral interface, so the credit engine never depends on a single aggregator.
   677→
   678→- **Request:** a unique reference, country, commodity (airtime, data or electricity), amount in minor units, and the phone number or meter number.
   679→- **Three possible results:** *success* (delivered, with a reference and any token), *failed* (definitely not delivered, with a code and a flag saying whether another provider may be tried), and *unknown* (no way to tell).
   680→- **Routing:** providers are ranked by priority and filtered by country and commodity. After repeated failures a provider is skipped for a cooling period.
   681→- **The key safety rule:** the router moves to the next provider only after a definite failure. An unknown result (a timeout, a server error, an unreadable reply) stops the chain, because the airtime or token may already have been delivered. It is looked up with the same provider, never sent to a second one.
   682→- **One delivery per reference:** repeating a reference returns the stored result and never vends again.
   683→- **Meter validation** is available before an electricity advance is offered.
   684→- **Configuration-driven adapter:** a new supplier needs one configuration object that says how to build each call and read each reply. The adapter treats server errors and timeouts as unknown and rate limits as retryable failures.
   685→- **Sandbox provider:** a mock supplier with success, failure, timeout and error modes for development and tests.
   686→
   687→**Onboarding a supplier:** agreement and sandbox credentials, then the supplier's documentation, then the configuration object, then contract tests against the sandbox, then a shadow run, then live at low volume, then promotion to primary or failover.
   688→
   689→**Delivery orchestration:** the advance is issued first, then the item is delivered. A definite failure reverses the advance exactly. An unknown result holds the advance as pending: it blocks a second advance and is not recovered until delivery is confirmed. A daily job settles pending deliveries by looking them up.

   727→## 18. Float funding: a structure that still works in 2050
   728→
   729→### 18.1 The decision
   730→
   731→Groway does not rely on one lender. It runs a **funder-agnostic capital mesh**: any number of funding facilities, each held as data (currency, countries, products, limit, price, performance triggers), with the platform allocating each advance to the best eligible facility. Groway seeds the first-loss layer and a senior lender funds the rest, per currency.
   732→
   733→### 18.2 Principles
   734→
   735→1. **Match currency.** Rand assets are funded in rand and kwacha assets in kwacha. A kwacha advance is never funded from a rand facility. Offshore money enters Malawi only with a hedge or a development lender that carries the currency risk.
   736→2. **Fund short assets with revolving lines.** Advances turn over in days, so the need is working capital: a revolving receivables facility sized to peak float, not a long-term loan.
   737→3. **Layer the capital.** Supplier terms first, a senior revolving facility second, a first-loss layer from Groway or an impact or guarantee provider third, and later additional funders as the book proves itself.
   738→4. **Performance triggers as code.** Minimum recovery rate and maximum charge-off are rules in the platform. A breach suspends new draws automatically and resumes when performance recovers, with no argument about definitions.
   739→5. **Show funders the truth in real time.** Read-only reporting from the ledger: balances, vintages, roll rates, recovery and losses.
   740→6. **Never hard-code a funder.** New funding sources, including pension funds, development lenders, impact funds and whatever digital-native sources exist in the future, are added by configuration through the same interface.
   741→7. **Ring-fence.** Hold funded receivables in a separate vehicle or account structure so funders have a clear claim, and keep funders' money separate from Groway's own.
   742→8. **Stress and diversify.** Test the book against recovery drops and funder withdrawal; keep at least two funders per currency once volume allows.
   743→
   744→### 18.3 Layers
   745→
   746→| Layer | Source | Role | Starting point |
   747→| --- | --- | --- | --- |
   748→| 1. Supplier credit | Aggregators and operators | Pay for airtime and tokens on terms, so float is partly funded by the supplier | Negotiate in each supplier agreement |
   749→| 2. Senior revolving facility | Bank or development lender, one per currency | Main float | One rand facility, one kwacha facility |
   750→| 3. First loss | Groway, impact funder or guarantee | Absorbs early losses so seniors accept the risk | Groway seeds a defined amount |
   751→| 4. Growth funding | Additional lenders and markets | Scale beyond the first facilities | After two clean cohorts |
   752→
   753→### 18.4 Sizing the float
   754→
   755→Peak float is daily advances times the days an advance stays outstanding, plus a buffer. For example, R10,000 of advances a day, outstanding on average about 7 days, with a 20% buffer needs R84,000. The platform calculates this from live data and alerts when headroom falls below a threshold.
   756→
   757→### 18.5 Status
   758→

Not built: persistence, funder reporting screens, and concentration limits.

   761→## 19. Launch order and the TNM proposition
   762→
   763→### 19.1 Merchant float launches first
   764→
   765→Yes: launch merchant float before customer advances. Reasons: you see every merchant sale, so recovery comes from settlements you control; the group is small and known; there is no consumer credit exposure yet; and it proves the ledger, recovery, funding and reconciliation in a controlled setting before consumers are involved.
   766→
   767→| Stage | Scope | Gate to the next stage (starting points for the credit committee) |
   768→| --- | --- | --- |
   769→| 0 | Internal test with staff accounts in the sandbox | Tests pass; reconciliation clean |
   770→| 1 | A small group of merchants with low caps | Recovery on target for two full cohorts; no unexplained ledger differences |
   771→| 2 | A wider merchant group | Loss within the base case; funding headroom healthy; complaints handled |
   772→| 3 | Customer advances in one Groway channel, small limits | Consent, disclosure and fraud checks proven; legal opinion in hand |
   773→| 4 | Electricity advances | Vending hook working; vendor agreement signed |
   774→| 5 | Malawi | Provider and partner agreements; registration route confirmed |
