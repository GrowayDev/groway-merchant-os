     5→# Groway Ticketing: Build Architecture & Implementation Guide
     6→
     7→**Scope:** A multi-country ticketing platform for cinema and events, built as a new module inside the existing Next.js modular monolith, running on AWS RDS PostgreSQL in af-south-1 (Cape Town), with a Mac-based staging environment and a phased migration to AWS.
     8→
     9→**Locked decisions:**
    10→
    11→| Decision | Choice |
    12→|---|---|
    13→| Markets | South Africa (Phase 1), Malawi (Phase 2) |
    14→| Customer types | Cinema chains **and** event organisers from day one |
    15→| Settlement | **Both** platform-settled and organiser-settled |
    16→| Country routing | Path prefix (`/za/`, `/mw/`) |
    17→| Database | AWS RDS PostgreSQL, af-south-1 |
    18→| Orchestration | Postgres-backed state machine + `SKIP LOCKED` job queue (Redis-free in Phase 0) |
    19→| Primary SA rail | **PayShap first**, via Peach Payments |
    20→| Fee model | Hybrid: 1.5% platform fee + R2.00 per paid ticket |
    21→| First pilot | Event organiser |
    22→| Staging | Mac behind Cloudflare tunnel, launchd-managed workers |

    68→## 2. Module design inside the monolith
    69→
    70→Ticketing follows the existing module-boundary convention: its own Prisma models, API routes, and UI components, sharing one database and one process.
    71→
    72→```
    73→src/modules/ticketing/
    74→├── catalog/          Event, Performance, SeatMap, Venue
    75→├── inventory/        Seat state, holds, release sweeps
    76→├── booking/          State machine, transitions, outbox emission
    77→├── ticketing/        Ticket issuance, HMAC-signed QR, check-in
    78→├── org/              Organisers, fee schedule, settlement mode
    79→├── payments/         Rail registry + adapters (moved from consumer-wallet)
    80→└── api/              Route handlers
    81→```
    82→
    83→**Movement of existing code:** The `MobileMoneyOrchestrator` class and its payment routes move into `src/modules/ticketing/payments/` without changing their public method signatures (`deposit`, `payout`, `getStatus`, `refund`). The `setTimeout` bodies are replaced by job enqueues. Existing call sites require no change.
    84→
    85→**What stays where it is:** CatalogProduct/POSLayout remain the box-office and on-site sales interface; they call ticketing inventory APIs rather than duplicating seat logic. GroSupply is untouched.

   192→## 4. Orchestration: state machine, not workflow engine
   193→
   194→You do not need Temporal, Argo, or BullMQ. The combination of an explicit state machine table and a Postgres queue gives durable retries, idempotency, and replay-equivalent recovery without new infrastructure.
   195→
   196→### 4.1 Booking state machine
   197→
   198→| From | To | Trigger | Side effects |
   199→|---|---|---|---|
   200→| — | `SEATS_HELD` | User selects seats | Postgres `UPDATE seats … WHERE state='AVAILABLE' RETURNING`; insert transition; enqueue `payment` job |
   201→| `SEATS_HELD` | `PENDING_PAYMENT` | Payment initiated | Outbox `booking.pending`; rail adapter returns redirect/request reference |
   202→| `PENDING_PAYMENT` | `AWAITING_CONFIRMATION` | Timeout or async rail | Outbox `payment.awaiting` |
   203→| `PENDING_PAYMENT` / `AWAITING_CONFIRMATION` | `CONFIRMED` | Webhook or reconciliation success | Outbox `booking.confirmed`; ledger postings; ticket issuance |
   204→| `PENDING_PAYMENT` | `EXPIRED` | Hold sweep | Seats released; outbox `seat.released` |
   205→| `CONFIRMED` | `REFUNDED` | Organiser or system action | Reverse ledger postings; void ticket |
   206→
   207→Every transition is written to `booking_transitions` with a unique `(bookingId, toState, idempotencyKey)`. Re-delivering a webhook is a no-op because the idempotency key already exists. **Replay = re-driving the state machine from the transitions table** by querying the rail's status API and posting the resulting event; there is no workflow DAG to re-run.
   208→
   209→### 4.2 Job queue with `SKIP LOCKED`
   210→
   211→```sql
   212→UPDATE jobs
   213→SET locked_at = now(), locked_by = $workerId, attempts = attempts + 1
   214→WHERE id = (
   215→  SELECT id FROM jobs
   216→  WHERE queue = $queue AND run_at <= now() AND locked_at IS NULL
   217→  ORDER BY run_at
   218→  FOR UPDATE SKIP LOCKED
   219→  LIMIT 1
   220→)
   221→RETURNING *;
   222→```
   223→
   224→Retries use exponential backoff written back to `run_at`. Failed jobs after N attempts move to a dead-letter state and emit an outbox alert event. This is the entire queueing system — no Redis, no BullMQ, no ioredis/Bun compatibility risk.
   225→
   226→### 4.3 Seat locking without Redis
   227→
   228→```sql
   229→UPDATE seats SET state='HELD', held_until = now() + interval '10 minutes'
   230→WHERE performance_id = $1 AND label = ANY($2) AND state='AVAILABLE'
   231→RETURNING label;
   232→```
   233→
   234→If fewer rows are returned than requested, release the held ones in the same transaction and return `SEATS_UNAVAILABLE`. The hold expiry worker runs every 60 seconds:
   235→
   236→```sql
   237→UPDATE seats SET state='AVAILABLE', held_until = NULL
   238→WHERE state='HELD' AND held_until < now()
   239→RETURNING id;
   240→```
   241→
   242→Redis becomes an **additive contention filter** in Phase 3 (`SET seat:{id} NX PX 600000` before the Postgres write) and does not change the authority model.

   246→## 5. Payments: PayShap-first adapter design
   247→
   248→### 5.1 Uniform adapter contract
   249→
   250→```typescript
   251→interface PaymentAdapter {
   252→  country(): CountryCode;
   253→  rail(): RailCode;
   254→  authorise(req: PaymentRequest): Promise<PaymentResult>;  // idempotent on req.id
   255→  capture(ref: ProviderRef): Promise<PaymentResult>;
   256→  refund(ref: ProviderRef, amountMinor: bigint): Promise<RefundResult>;
   257→  parseWebhook(payload: unknown): WebhookEvent;
   258→  supportedMethods(): Set<PaymentMethod>;
   259→}
   260→```
   261→
   262→The webhook route at `/api/consumer/mobile-money/webhook/[provider]` becomes: **parse → verify signature → write outbox event → return 200**. Nothing happens synchronously. The worker consumes the outbox event and drives the state machine.
   263→
   264→### 5.2 PayShap via Peach Payments
   265→
   266→Peach Payments offers PayShap at **R1.50 + R1.50 per transaction on the SME package**, with instant settlement and lower fraud risk than card. PayShap Request (request-to-pay) is available through Peach and other infrastructure providers such as Stitch and Electrum, where the payer approves the request in their own banking app.
   267→
   268→**Integration path for Phase 1:**
   269→
   270→1. **Merchant onboarding:** Open a Peach Payments SME account. Confirm in writing whether PayShap can be configured for **direct-to-organiser settlement** (funds land in the organiser's bank account, not Groway's). This is the single most important commercial question before Phase 1 payment work begins.
   271→2. **Request-to-pay flow:** If direct-to-organiser is supported, the adapter creates a PayShap request against the organiser's merchant reference; the buyer approves in their banking app; Peach sends a webhook; the worker confirms the booking. Groway's ledger records only the **fee transaction**, not the ticket revenue.
   272→3. **If direct-to-organiser is not supported by Peach:** the adapter falls back to platform-settled mode for PayShap, with an immediate payout step to the organiser. This is operationally heavier and should be treated as a Phase 1.5 enhancement, not the default.
   273→
   274→**Rail priority for South Africa:**
   275→
   276→| Priority | Rail | Adapter status | Settlement support |
   277→|---|---|---|---|
   278→| 1 | **PayShap (Peach)** | Phase 1 | Organiser-direct (pending Peach confirmation) |
   279→| 2 | **PayFast** | Phase 1 | Organiser-direct |
   280→| 3 | **Ozow** | Phase 1 | Organiser-direct |
   281→| 4 | **Yoco** | Phase 2 | Organiser-direct |
   282→
   283→### 5.3 What not to build
   284→
   285→- Do not register M-Pesa or MTC Maris against South Africa or Malawi. M-Pesa operates in Kenya, Tanzania, Mozambique, DRC, and Lesotho; MTC Maris operates in Namibia. They belong in the registry only when those countries are enabled.
   286→- Do not mark up PayShap processing. Pass it through at R3.00 total (R1.50 + R1.50) and let its low cost be the commercial wedge.

   290→## 6. Dual settlement ledger
   291→
   292→Your existing `ConsumerWallet` and GroCore ledger become the settlement authority for **platform-settled** bookings. For **organiser-settled** bookings, Groway never holds ticket revenue — it records only the fee.
   293→
   294→### 6.1 Ledger changes (Phase 0)
   295→
   296→| Change | Detail |
   297→|---|---|
   298→| **Currency on every account** | `Account` gains `currency` and `exponent`. ZAR = 2, MWK = 2. |
   299→| **Integer minor units** | All money columns are `BigInt`; no floats anywhere in the money path. ZAR cents, MWK tambala. |
   300→| **Per-currency fee accounts** | `platform_fee_revenue:ZAR`, `platform_fee_revenue:MWK`. |
   301→| **Single-currency constraint** | `CHECK` constraint on every double-entry transaction: debits and credits must share a currency. No cross-currency postings in v1. |
   302→
   303→### 6.2 Posting rules by settlement mode
   304→
   305→**Platform-settled (organiser wants Groway to collect and pay out):**
   306→
   307→| Event | Debit | Credit |
   308→|---|---|---|
   309→| Booking confirmed | `gateway_clearing` (gross) | `organiser_payable` (net) + `platform_fee_revenue` (fee) |
   310→| Payout to organiser | `organiser_payable` | `organiser_wallet` / bank |
   311→| Refund | Reverse all three proportionally | |
   312→
   313→**Organiser-settled (organiser uses their own PayShap/PayFast account; Groway never holds revenue):**
   314→
   315→| Event | Debit | Credit |
   316→|---|---|---|
   317→| Booking confirmed | `organiser_receivable` (fee only) | `platform_fee_revenue` (fee) |
   318→| Monthly invoice settlement | Bank / cash | `organiser_receivable` |
   319→| Refund (organiser refunds buyer via their own rail) | Reverse fee receivable per contract | `platform_fee_revenue` |
   320→
   321→The same booking state machine drives both modes; only the ledger posting step branches on `settlementMode`. **Both rule sets ship in Phase 0, tested against simulated rails.** Live PayShap wiring is Phase 1.
   322→
   323→### 6.3 Why organiser-settled is the commercially critical mode in SA
   324→
   325→The SA ticketing market has a zero-platform-fee challenger (TKKT, R0 platform fee, funds land in the organiser's own gateway) and an incumbent with a published transparent rate (Quicket at 4.9% ex VAT combined plus R7.50 per ticket). Larger event organisers and cinema chains already have their own gateway relationships and will expect organiser-settled as the default. Platform-settled is the Malawi default and the SA small-organiser default. **Do not treat organiser-settled as the afterthought** — it is the mode most likely to win your first serious SA customer.

   348→### 7.2 Worked example (SA event, R200 ticket, PayShap)

   351→|---|---|---|

   362→

   371→## 8. Country isolation and path-prefix routing
   372→
   373→### 8.1 Routing middleware
   374→
   375→```
   376→/za/*  → rewrite to /*, set x-country: ZA
   377→/mw/*  → rewrite to /*, set x-country: MW
   378→/api/* → no rewrite; country from authenticated session, admin override only
   379→```
   380→
   381→Public URLs carry the prefix (`/za/events/...`) for SEO and sharing. API routes never move. A `buildUrl(path, country)` helper is enforced by lint rule — raw internal links fail CI.
   382→
   383→### 8.2 Three enforcement layers
   384→
   385→| Layer | Mechanism |
   386→|---|---|
   387→| **Routing** | Middleware rejects requests where `x-country` disagrees with the session `countryCode` (admin excepted). |
   388→| **Application** | Prisma extension injects `countryCode` into every tenant-scoped query and sets `app.country` for RLS. |
   389→| **Database** | RLS policy on every tenant-scoped table. A missing filter fails at the DB level, not silently. |
   390→
   391→### 8.3 Data isolation
   392→
   393→Single RDS cluster in af-south-1 (closest region to both markets; no Malawi region exists). `countryCode` on every tenant-scoped model; no cross-country foreign keys. Redis (Phase 3) uses `{country}:` key prefixes. Outbox events carry `countryCode`; workers route to country-scoped queues.
   394→
   395→**Latency note:** Malawi users will see ~40–60 ms RTT to af-south-1 permanently. Design for short write paths, no N+1 queries, and aggressive catalog caching at the edge. Measure from a Blantyre vantage point in Phase 2, not from Cape Town.

   399→## 9. Deployment architecture
   400→
   401→### 9.1 RDS configuration
   402→
   403→| Parameter | Value | Rationale |
   404→|---|---|---|
   405→| **Instance class** | `db.t3.medium` | 2 vCPU, 4 GiB RAM. Burstable is correct for spiky ticketing traffic. |
   406→| **AZ** | Single-AZ | Multi-AZ doubles cost for failover you do not need yet. |
   407→| **Storage** | gp3, 100 GB | Autoscaling enabled above 100 GB. |
   408→| **Region** | af-south-1 (Cape Town) | Closest to both markets. |
   409→| **Backups** | Automated, 7-day retention | Non-negotiable. |
   410→| **Performance Insights** | Enabled (free tier) | See top SQL and lock waits during first on-sale. |
   411→| **Log retention** | 7 days | Verbose logging is a silent cost explosion. |
   412→| **RDS Proxy** | **Not enabled** | Long-lived app + worker processes; use standard pooling. |
   413→
   414→**Cost:** `db.t3.medium` in af-south-1 is **$0.093/hour = $67.89/month** for Single-AZ on-demand. Multi-AZ is $0.186/hour ($136/month). Storage at gp3 rates adds a small amount. This is the correct starting size for a startup with one pilot organiser.
   415→
   416→**Connection pooling:** cap Prisma pools at 8 connections for the app and 5 for the worker (total ≤13, well under `max_connections` for `db.t3.medium`). If you run multiple app instances later, add **PgBouncer** in front — cheaper and more predictable than RDS Proxy at this scale.
   417→
   418→### 9.2 Mac staging environment
   419→
   420→| Component | Configuration |
   421→|---|---|
   422→| **App** | `bun run dev` on port 3000, launchd `KeepAlive=true`. |
   423→| **Worker** | `bun run worker` as a separate launchd service, `KeepAlive=true`. |
   424→| **Sleep prevention** | `caffeinate -s` in the launchd wrapper. |
   425→| **Tunnel** | Cloudflare tunnel exposes **only** the app port. Worker has no inbound route; it dials out to RDS. |
   426→| **RDS security group** | Must allow the Mac's egress IP. Use a security group referencing a dynamic DNS record or run through a bastion — a static IP will break within a week. |
   427→| **Health check** | `/health` route reports queue depth and worker heartbeat. |
   428→
   429→### 9.3 Worker separation
   430→
   431→The worker **must not** run inside Next.js API routes. A separate entrypoint (`bun run worker`) in its own process from day one. CI should reject any import of worker code into `src/app/api/`. When you later move the app to AWS, the worker becomes its own container or ECS service; the app can remain on Vercel or move to ECS independently.

   556→## 11. Operational runbook
   557→
   558→| Scenario | Action |
   559→|---|---|
   560→| **Worker heartbeat missed >60s** | Alert; check launchd status; restart worker; queue is durable so no jobs are lost. |
   561→| **RDS CPU credits exhausted** | Move to `db.m5.large` or `db.r6g.large`. Monitor `CPUCreditBalance`; this is a resize, not a redesign. |
   562→| **PayShap webhook lost** | Reconciliation worker queries Peach status API; posts resulting event; state machine confirms or fails. |
   563→| **Seat lock split-brain (Phase 3)** | Postgres is authority; Redis lock overwritten by expiry sweep. |
   564→| **Cross-country access attempt** | Middleware 403; log as security event; CI test authenticates as MW user and hits all `/za/` routes expecting 403. |
   565→| **Mac sleeps despite `caffeinate`** | launchd `KeepAlive` restarts processes; job queue holds work; alert on heartbeat gap. |
   566→| **Ledger imbalance** | Nightly invariant job: debits = credits per currency per day. Alert on drift. |

   584→
   585→1. **Peach Payments PayShap direct-to-organiser settlement** — the single highest-priority commercial confirmation. If Peach cannot support it, the PayShap adapter's settlement design changes, and the Phase 1 critical path gains a payout step.

   592→## 14. Summary: what makes this architecture correct for Groway
   593→
   594→1. **It uses what you have.** The modular monolith, GroCore ledger, wallet, and existing route tree are preserved. Ticketing is a new module, not a new platform.
   595→2. **It adds no infrastructure you do not need yet.** Postgres does locking, queueing, and orchestration in Phase 0. Redis, brokers, and workflow engines arrive only when a measured trigger demands them.
   596→3. **It treats the ledger as the hardest thing to retrofit.** Dual settlement and integer minor units ship in Phase 0, before any live money moves.
   597→4. **It is shaped by the SA market, not imported from elsewhere.** PayShap-first, hybrid fee below Quicket, organiser-settled supported from day one, and a zero-fee challenger acknowledged as the competitive reference point.
   598→5. **It is operationally honest about the staging environment.** Mac + launchd + Cloudflare tunnel + RDS is a real staging setup if the worker is separated and the queue is durable. It does not pretend to be production; it is the correct stepping stone to it.
   599→
   600→The next concrete action is **G4 (Peach PayShap onboarding and settlement confirmation)**, because its outcome determines whether the Phase 1 PayShap adapter is a two-party or three-party money flow — and that determines the Phase 1 critical path.
